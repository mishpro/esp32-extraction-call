# Журнал решений (ADR)

Формат: контекст → решение → последствия. Статус: `принято` (все), если не указано иное.
Дополняет `README.md` §3; при расхождении этот файл — объяснение «почему», а не замена плану.

---

### ADR-0001 — Транспорт: `ws://` без TLS
**Контекст:** VPS со статическим IP, TLS требует CA-бандла в прошивке MicroPython (certifi для uV нет) + верных часов на кнопке.
**Решение:** `ws://<host>:8000/ws`, шифрование отложено.
**Последствия:** токены идут открытым текстом; в MVP авторизация выключена (ADR-0011). Для боевого режима — отдельный шаг с доменом и `wss`.

### ADR-0002 — Протокол: `drafts/Протокол.md` v1.0
**Контекст:** в документе описаны все три реализации.
**Решение:** реализуем по документу как есть: тип в поле `t`, плоский JSON (без вложенного `payload`), поля `v`/`seq`/`t_epoch`.
**Последствия:** машинная выжимка в `plan/schema/messages.schema.json`, проверяется скриптом `plan/schema/validate_examples.py` (13/13 примеров валидны). При правке документа — правим схему следом.

### ADR-0003 — Сервер: Python 3.12 + FastAPI + uvicorn
**Контекст:** нужно HTTP (диагностика) и WS в одном процессе, 1 vCPU / 1 GB.
**Решение:** FastAPI + `uvicorn[standard]` + Pydantic v2; зависимости через `uv`.
**Последствия:** uvicorn имеет собственный WS-ping — развести с протокольным heartbeat.

### ADR-0004 — Прошивка: MicroPython 1.29.0
**Контекст:** ESP32-WROOM-32 (клом DOIT DevKit V1), PlatformIO MicroPython не поддерживает (фреймворки только arduino/espidf/ulp).
**Решение:** MicroPython 1.29.0, `esptool` 5 + `mpremote`, Thonny не нужен.
**Последствия:** `legacy/` остаётся Arduino-справкой по железу и в новом стеке не участвует.

### ADR-0005 — WS-клиент кнопки пишем вручную
**Контекст:** в `micropython-lib` WS-клиента нет; `extmod/modwebsocket.c` — WebREPL-сервер; §7 Протокола требует свой клиент.
**Решение:** свой клиент по §7 (handshake, маскирование, фрагментация, `select.poll`).
**Последствия:** ядро парсинга кадров держим без uV-импортов → тестируется на CPython.

### ADR-0006 — Приложение: нативное Android
**Контекст:** нужен push в фоне и надёжная связь; Web Push в нативном приложении не существует.
**Решение:** Kotlin + Compose, OkHttp 5.5.1 WebSocket внутри Foreground Service, `StateFlow` наружу, AGP 9.6 / JDK 17 / minSdk 26 / target 36.
**Последствия:** нужен Android SDK на станции (~4–6 ГБ, место есть); сборка только на реальном телефоне.

### ADR-0007 — Push: FCM
**Контекст:** FCM требует GMS на телефоне; Web Push недоступен в нативном приложении.
**Решение:** FCM — целевой канал (S6); в MVP — локальное уведомление от Foreground Service по WS.
**Последствия:** на телефонах без GMS push не придёт, но уведомление всё равно будет (локальное). `firebase-expert` поставить на S6.

### ADR-0008 — MVP односторонний
**Контекст:** вертикальный срез «кнопка → WS → приложение».
**Решение:** MVP реализует только путь сигнала; `timer`/`cancel`/отсчёт — S4.
**Последствия:** `timer`, `cancel`, состояния `COUNTDOWN`/`ARRIVED` в схеме есть (для совместимости), но в MVP не используются.

### ADR-0009 — Дисплей: один экран со статус-баром
**Контекст:** 128×64, нужен статус WS, доступность приложения, состояние и метка времени.
**Решение:** один экран: строка 0 — `WS:OK APP:ON`, ниже — `TIME`, `STATE:`, `LAST`, `SEQ`. Шрифт 8×8 даёт 16 символов в строке, поэтому время вынесено на отдельную строку (уточнено на S2).
**Последствия:** отдельных экранов нет; шрифт — встроенный PETME128 8×8 (`framebuf.text()`), свой шрифт не нужен.

### ADR-0010 — Конфиг кнопки: `config.py` в MVP, BLE — S5
**Контекст:** BLE-провижининг целевой, но упирается в GATT-реализацию на uV.
**Решение:** MVP — `config.py` через `mpremote`; BLE переносится на S5.
**Последствия:** смена WiFi/адреса сервера требует USB — терпимо на стенде.

### ADR-0011 — Авторизация выключена в MVP
**Контекст:** один комплект «кнопка + приложение», §4.1 предусматривает токен.
**Решение:** код проверки токена (SHA-256 + `hmac.compare_digest`) реализуется сразу, но включается флагом `AUTH_REQUIRED=false`.
**Последствия:** сервер в MVP принимает любой `hello` с корректной ролью и `id`.

### ADR-0012 — Время: сервер — источник истины, NTP не нужен
**Контекст:** кнопке нужно абсолютное время для меток; NTP может быть недоступен.
**Решение:** каждое сообщение несёт `t_epoch`; кнопка считает смещение, таймер (S4) — по `deadline_t`. `ntptime` — опциональный fallback.
**Последствия:** без TLS требований к часам нет; метка «нет синхронизации» до первого сообщения сервера.

### ADR-0013 — Deep sleep отложен
**Контекст:** требование «экран показывает доступность приложения» предполагает постоянное соединение.
**Решение:** до S7 кнопка работает постоянно; deep sleep (wake по ext0 GPIO4) — вместе с питанием.
**Последствия:** в MVP кнопка питается от USB.

### ADR-0014 — Питание отложено
**Контекст:** схема зависит от типа батареи и режима «аккумулятор + USB-C одновременно».
**Решение:** не выбираем сейчас; заготовка — TP5100 (зарядка с load-sharing) + boost 5 В + диодная развязка + тумблер питания на батарейной ветке.
**Последствия:** тумблер питания в MVP — внешний, на проводе.

### ADR-0015 — `drafts/ТЗ.md` не читаем
**Контекст:** файл большой, пользователь запретил его чтение.
**Решение:** план строится на требованиях из исходного запроса + `drafts/Протокол.md`.
**Последствия:** требования из ТЗ, не отражённые в запросе, в план не попадут — риск принят осознанно.

### ADR-0016 — Скиллы из экосистемы
**Контекст:** локального набора не хватало на Android/Kotlin и WS-сервер.
**Решение:** установлены `fastapi-expert`, `websocket-engineer` (S1) и `compose`, `kotlin-coroutines`, `kotlin-flows`, `gradle-build-performance` (S3). Отложены `firebase-expert` (S6) и `websocket-security` (после auth/TLS).
**Последствия:** раскладка зафиксирована в `plan/skills.md`.

### ADR-0017 — Foreground service: тип `specialUse`
**Контекст:** приложению нужен постоянный WS-канал 24/7. На Android 15+ тип `dataSync` ограничен 6 часами в сутки и не подходит.
**Решение:** `android:foregroundServiceType="specialUse"` + `FOREGROUND_SERVICE_SPECIAL_USE` + свойство `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` с описанием причины. Приложение не публикуется в Google Play, поэтому review не нужен.
**Последствия:** лимита 6 часов нет; на реальных телефонах всё равно нужна настройка «батарея без ограничений» (Nothing OS и другие OEM любят усыплять фон).

### ADR-0018 — Связь сервиса и UI: process-wide `SignalBus`
**Контекст:** foreground-сервис живёт дольше Activity; нужен простой способ отдавать состояние без Binder-обвязки.
**Решение:** `object SignalBus` с `StateFlow<SignalState>`; `SignalService` пишет, Activity читает через `collectAsStateWithLifecycle`. Сервис управляется через `SignalService.start/stop`.
**Последствия:** минимум кода для MVP; состояние не переживает процесс (при убийстве процесса UI пуст до перезапуска сервиса). При необходимости в S6 можно заменить на `WorkManager`/binding без изменения экрана.

### ADR-0019 — Идентичность нажатия в приложении: `(from, seq, t_epoch)`
**Контекст:** `seq` у кнопки — монотонный счётчик от 1, но он **не хранится** и после каждой перезагрузки начинается заново. Сервер сбрасывает watermark при первом `press` с `seq=1` в новой сессии и принимает его. Приложение, дедуплицирующее только по `seq`, теряло бы первый вызов после каждой перезагрузки кнопки (и вызовы от второго устройства с тем же `seq`).
**Решение:** дубликатом считается только совпадение `(from, seq, t_epoch)`; уведомление получает id по `seq`, поэтому активное уведомление о вызове обновляется, а не плодится.
**Последствия:** перезагрузка кнопки и смена устройства больше не теряют нажатия; сервер по-прежнему остаётся единственным местом строгой дедупликации по `seq`.
