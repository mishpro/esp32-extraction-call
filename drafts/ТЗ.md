## 1. Назначение системы

Guidecaller — программно-аппаратный комплекс «кнопка ожидания» для игры в эвакуацию.

Один человек (далее **А**) находится у кнопки. Второй человек (далее **Б**) находится в другом месте и имеет смартфон с приложением. А нажимает кнопку — Б получает сигнал. Б вводит, через сколько времени он прибудет, и подтверждает отправку. У А на дисплее кнопки запускается обратный отсчёт до этого момента.

Система состоит из трёх узлов:

```
   ┌─────────────────┐        ws:// + токен        ┌──────────────────┐        ws:// + токен        ┌─────────────────────┐
   │  Кнопка (ESP32) │◄────────────────────────────►│  WS-сервер (VPS) │◄────────────────────────────►│ Приложение (Android)│
   │  OLED, пьезо,   │        press / timer / ack    │  маршрутизация,   │        press / timer / ack    │  Foreground Service │
   │  кнопка, deep   │        status / heartbeat     │  состояние, логи  │        status / heartbeat     │  локальные уведомл. │
   │  sleep          │                              │                  │                              │                     │
   └─────────────────┘                              └──────────────────┘                              └─────────────────────┘
```

Кнопка никогда не обращается к приложению напрямую и никогда не обращается к Telegram. Telegram-вариант из черновика `helpful materials.md` исключён: обмен идёт только через WS-сервер.

### 1.1 Глоссарий

| Термин | Значение |
|---|---|
| **Кнопка** | Устройство на базе ESP32: OLED-дисплей, тактовая кнопка, пьезо-бузер, светодиоды, питание от аккумулятора и/или USB-C |
| **Приложение** | Android-приложение (Kotlin + Jetpack Compose), устанавливаемое в обход Play Market |
| **Сервер** | Процесс на VPS: WebSocket-брокер приложения и кнопки, хранитель состояния |
| **WS-сервер** | WebSocket-эндпоинт `ws://host:port/ws`, аутентификация по токену |
| **Сессия** | Одно TCP-соединение клиента с сервером |
| **Сигнал** | Событие нажатия кнопки, доставленное от кнопки приложению |
| **ETA** | Длительность обратного отсчёта, введённая человеком Б (в секундах) |
| **Отсчёт** | Обратный отсчёт на OLED кнопки |
| **ACK** | Подтверждение получения сообщения (delivery-гарантия) |
| **Живость** | Состояние «клиент подключён и отвечает» |
| **ARMED** | Кнопка подключена, ждёт нажатия |
| **IDLE-сон** | Кнопка спит в deep sleep между игровыми сессиями |

### 1.2 Роли

| Роль | Что имеет | Что делает |
|---|---|---|
| **А** (владелец кнопки) | Кнопка | Нажимает кнопку, читает отсчёт и статус на OLED |
| **Б** (владелец смартфона) | Приложение | Получает уведомление, вводит ETA, подтверждает |
| **Администратор** | SSH/консоль VPS, конфиг приложения | Разворачивает сервер, выдаёт токен, читает логи |

### 1.3 Границы объёма (out of scope)

- Не входит: публикация в Play Market, аккаунты, синхронизация между несколькими кнопками, групповые чаты, веб-клиент.
- Не входит: Telegram-бот, любые внешние push-провайдеры (FCM — отдельный可选ный релиз, см. FR-A-09).
- Не входит: определение местоположения, карты, маршруты.
- Не входит: несколько комплектов «кнопка ↔ приложение» (архитектура это допускает, см. FR-S-02, но UI не реализует).

## 2. Сценарии использования

### 2.1 Основной сценарий

| ID | Сценарий |
|---|---|
| UC-01 | А нажимает кнопку → у Б всплывает уведомление «Кнопка нажата» |
| UC-02 | Б вводит ETA и подтверждает → у А на OLED идёт обратный отсчёт |
| UC-03 | Отсчёт доходит до нуля → у А звучит сигнал и на OLED появляется сообщение |
| UC-04 | Приложение закрыто/фоновое — уведомление всё равно приходит |
| UC-05 | Кнопка вне зоны Wi-Fi или выключена → приложение показывает «кнопка недоступна» |
| UC-06 | Кнопка вне зоны Wi-Fi → на OLED горит индикатор «нет сервера» |

### 2.2 Критерии приёмки (EARS-стиль)

| ID | Критерий |
|---|---|
| AC-01 | **Когда** А нажимает кнопку **и** кнопка подключена к серверу, **то** приложение показывает уведомление не позднее чем через 2 с (p95) |
| AC-02 | **Когда** Б подтвердил ETA **и** кнопка подключена, **то** на OLED появляется обратный отсчёт не позднее чем через 2 с (p95) |
| AC-03 | **Когда** отсчёт достиг нуля, **то** кнопка издаёт звуковой сигнал **и** показывает текст `ARRIVED` в течение 1 с |
| AC-04 | **Когда** приложение не на переднем плане, **то** уведомление о нажатии всё равно появляется |
| AC-05 | **Когда** кнопка не отвечает дольше 90 с, **то** приложение показывает статус «кнопка недоступна» не позднее чем через 120 с |
| AC-06 | **Когда** кнопка не может доставить сигнал (нет ACK сервера за 30 с), **то** на OLED появляется `NO ACK` **и** звучит сигнал ошибки |
| AC-07 | **Когда** Б вводит ETA, **то** значение проверяется: 60 с ≤ ETA ≤ 86400 с; при выходе за границы ввод блокируется с пояснением |
| AC-08 | **Когда** кнопка обесточена и включена заново во время отсчёта, **то** кнопка показывает `TIMER LOST` **и** ждёт новой команды (отсчёт не восстанавливается) |
| AC-09 | **Когда** сервер недоступен, **то** кнопка показывает `NO SERVER` и повторяет подключение с backoff |
| AC-10 | **Когда** приложение закрыто насильно, **то** уведомления не приходят до перезапуска приложения (принятое ограничение, см. FR-A-09) |

## 3. Архитектура

### 3.1 Узлы и их ответственность

**Кнопка (ESP32 + MicroPython)**
- Wi-Fi STA, подключение к точке доступа (SSID/пароль в конфиге на файловой системе).
- WebSocket-клиент (собственная реализация RFC 6455) с reconnect-логикой.
- Кнопка, OLED (SSD1306, I2C, 0x3C), пьезо-бузер (PWM), два светодиода.
- Модель питания: deep sleep между сессиями, active-режим во время сессии.
- Источник времени — **сервер**, не локальные часы (см. §6.3).

**Сервер (VPS, Python)**
- FastAPI + uvicorn: HTTP `/health`, `/api/status` и WebSocket `/ws`.
- Реестр сессий: `device_id → сессия`, `app_id → сессия`.
- Маршрутизация: `press` → приложению, `timer` → кнопке, `status` → обоим.
- Хранилище «последнего состояния» (последний ETA, последнее состояние кнопки) — переживает переподключение клиента.
- Логи в stdout → journald.

**Приложение (Android, Kotlin)**
- Foreground Service с постоянным WebSocket-соединением.
- Compose UI: статус сервера, статус кнопки, поле ввода ETA, кнопка подтверждения.
- Локальные уведомления через `NotificationManager`.
- Токен хранится в `EncryptedSharedPreferences`.

### 3.2 Модель состояний кнопки

```
                    ┌─────────┐
        power-on →  │  BOOT   │  инициализация I/O, чтение NVS
                    └────┬────┘
                         v
                  ┌─────────────┐   wifi fail
                  │ WIFI_CONNECT │<──────────────┐
                  └──────┬──────┘               │
                         │ ok                   │ backoff
                         v                      │
                  ┌─────────────┐  no ws        │
                  │   OFFLINE   │───────────────┘
                  │  NO SERVER  │
                  └──────┬──────┘
                         │ ws connected
                         v
                  ┌─────────────┐
                  │   ARMED     │◄──────────────┐
                  │  (ожидает)  │               │
                  └──────┬──────┘               │
                         │ press                │ таймер истёк / отменён
                         v                      │
                  ┌─────────────┐               │
                  │  SENT       │  ждём ACK     │
                  │ (no ack 30s)│──── error ────┘
                  └──────┬──────┘
                         │ ack(ok)
                         v
                  ┌─────────────┐
                  │  WAIT_ETA   │  ждём timer от приложения
                  └──────┬──────┘
                         │ timer
                         v
                  ┌─────────────┐
                  │  COUNTDOWN  │───► (по истечении) ───► ARRIVED ──┐
                  └──────┬──────┘                                  │
                         │ отмена (BTN2)                            │
                         └──────────────────────────────────────────┘
```

Состояние `ARRIVED` возвращает кнопку в `ARMED` через 60 с (или немедленно по нажатию BTN1).

### 3.3 Модель питания

| Режим | Когда | Wi-Fi | OLED | Примерный ток |
|---|---|---|---|---|
| **ACTIVE** | От нажатия до конца отсчёта | включён, сессия WS живая | включён, обновление 1 раз/с | 90–140 мА |
| **IDLE** | Между сессиями | выключен, deep sleep 60 с (пробуждение по таймеру или по BTN1) | выключен (`display off`) либо «мигание» | 10–50 мкА (MCU) + 5–10 мА (обвязка платы) |
| **STANDBY-OFF** | Тумблер питания выключен | — | — | < 1 мА |

Подробный расчёт и требования к железу — §8.

## 4. Функциональные требования

### 4.1 Кнопка (FR-K)

| ID | Требование | Критерий проверки |
|---|---|---|
| FR-K-01 | Кнопка при нажатии BTN1 формирует событие `press` и отправляет его серверу | В логах сервера `press` от `device_id` в течение 2 с после нажатия |
| FR-K-02 | Кнопка отображает на OLED состояние «сервер доступен» | На OLED присутствует индикатор `SRV` в светящемся/гаснущем виде |
| FR-K-03 | Кнопка отображает на OLED доступность приложения | Индикатор `APP` отражает `app_online` из последнего `status` |
| FR-K-04 | Кнопка показывает обратный отсчёт `HH:MM:SS` после получения `timer` | Экран содержит `03:00:00` через 2 с после `timer` |
| FR-K-05 | Кнопка показывает обратный отсчёт с точностью ±2 с на интервале 3 ч | Сверка с эталонным таймером: расхождение ≤ 2 с |
| FR-K-06 | Кнопка издаёт короткий звук при получении `timer` | Звуковой импульс 100 мс |
| FR-K-07 | По истечении отсчёта кнопка издаёт характерный сигнал и показывает `ARRIVED` | Звук + текст `ARRIVED` в течение 1 с после нуля |
| FR-K-08 | Кнопка показывает `NO ACK` и звук ошибки, если ACK не пришёл за 30 с | Разрыв связи: через 30 с — `NO ACK` + звук |
| FR-K-09 | Кнопка повторяет отправку `press` до 3 раз с интервалом 5 с при отсутствии ACK | В логах видно до 3 попыток `press` |
| FR-K-10 | Кнопка показывает `WAIT_ETA` между подтверждением сигнала и получением ETA | Экран содержит `WAIT ETA` |
| FR-K-11 | BTN2 отменяет активный отсчёт и возвращает кнопку в `ARMED` | Нажатие BTN2 → экран `ARMED` |
| FR-K-12 | Долгое нажатие (≥2 с) BTN2 переключает звук в режим mute | Повторное нажатие возвращает звук; состояние видно на экране (`MUTE`) |
| FR-K-13 | Кнопка показывает `TIMER LOST`, если при старте обнаружен незавершённый отсчёт, но время не восстановлено | Проверка: обесточить и включить во время отсчёта → `TIMER LOST` |
| FR-K-14 | Кнопка поддерживает deep sleep между сессиями и просыпается по таймеру (60 с) **или по нажатию BTN1** | Потребление в покое падает до уровня IDLE (замер §8); нажатие BTN1 в IDLE будит кнопку |
| FR-K-15 | Кнопка переживает потерю Wi-Fi: переподключается сама и показывает `NO SERVER` | Выключить точку доступа на 2 мин → `NO SERVER`, затем восстановление без перезагрузки |
| FR-K-16 | Кнопка восстанавливает состояние `ARMED` автоматически после перезагрузки | Перезагрузка по питанию → через ≤ 60 с на экране `ARMED` |
| FR-K-17 | Кнопка показывает версию прошивки и `device_id` по короткому нажатию BTN2 в `ARMED` | На экране `FW 1.0.0 / ID ab12` |
| FR-K-18 | Светодиод `LED OK` (GPIO 19) горит в `ARMED`, мигает в `ACTIVE`, гаснет в ошибке | Визуальная проверка по таблице §7.4 |
| FR-K-19 | Светодиод `LED ERR` (GPIO 2, встроенный в плату) горит при `NO SERVER` / `NO ACK` | Визуальная проверка |
| FR-K-20 | Кнопка не принимает новых нажатий, пока не истёк таймаут ожидания ACK (30 с) | Второе нажатие в окне игнорируется |

### 4.2 Сервер (FR-S)

| ID | Требование | Критерий проверки |
|---|---|---|
| FR-S-01 | Сервер принимает WS-подключения с аутентификацией по токену | Неверный токен → соединение закрывается кодом 4401 |
| FR-S-02 | Сервер различает роли клиентов (`device` / `app`) по полю `role` в `hello` | Клиент без роли отклоняется |
| FR-S-03 | Сервер маршрутизирует `press` от кнопки только подключённому приложению | Второе приложение (если появится) не получает чужой `press` |
| FR-S-04 | Сервер маршрутизирует `timer` от приложения только своей кнопке | `timer` доходит до адресата; посторонняя кнопка его не получает |
| FR-S-05 | Сервер подтверждает приём `press` и `timer` сообщением `ack` | В логах `ack` в течение 200 мс |
| FR-S-06 | Сервер передаёт `status` обеим сторонам при изменении живости клиента | Изменение живости приводит к `status` у второй стороны |
| FR-S-07 | Сервер хранит последнее состояние кнопки и последний ETA и отдаёт их при переподключении клиента | Новый `hello` → сервер шлёт `status` с сохранёнными данными |
| FR-S-08 | Сервер отправляет heartbeat-пинг каждые 15 с и закрывает сессию после 3 пропущенных пингов | Убитый клиент исчезает из реестра за ≤ 45 с |
| FR-S-09 | Сервер пишет структурированный лог: connect/disconnect, `press`, `timer`, `ack`, ошибки | Журнал `journalctl -u guidecaller` содержит события с `device_id`/`app_id` |
| FR-S-10 | Сервер никогда не пишет токен в лог и не требует его в URL | Токен передаётся только в теле `hello`; grep по журналу не находит токен |
| FR-S-11 | Сервер предоставляет `GET /health` → `200 {"ok":true}` и `GET /api/status` → состояние кнопки и приложения | `curl /health` → 200; `/api/status` содержит `device_online`, `app_online` |
| FR-S-12 | Сервер ограничивает длину входящего сообщения 4 КБ и отклоняет более крупные | Отправка 8 КБ → соединение закрыто |
| FR-S-13 | Сервер переживает перезапуск, сохраняя последнее состояние в файле на диске | Перезапуск сервиса → `/api/status` показывает прежний ETA |
| FR-S-14 | Сервер отклоняет `hello` с неверной ролью или без `device_id`/`app_id` | Соединение закрыто кодом 4400 |

### 4.3 Приложение (FR-A)

| ID | Требование | Критерий проверки |
|---|---|---|
| FR-A-01 | Приложение показывает статус соединения с сервером | В UI есть индикатор `SERVER: ONLINE/OFFLINE` |
| FR-A-02 | Приложение показывает доступность кнопки | В UI есть индикатор `BUTTON: ONLINE/OFFLINE` |
| FR-A-03 | Приложение показывает локальное уведомление при получении сигнала от кнопки | Уведомление «Кнопка нажата» с заголовком и временем |
| FR-A-04 | Приложение показывает локальное уведомление при смене статуса кнопки или сервера | Уведомление «Кнопка недоступна» / «Сервер недоступен» |
| FR-A-05 | Приложение даёт ввести ETA в минутах с быстрыми пресетами (15 мин, 30 мин, 1 ч, 2 ч, 3 ч) | Пресет `3 ч` подставляет `180` мин |
| FR-A-06 | Приложение валидирует ETA: 1…1440 минут, с пояснением при ошибке | Ввод `0` или `1500` → поле подсвечено, подтверждение заблокировано |
| FR-A-07 | Приложение отправляет `timer` только по явному подтверждению пользователя (кнопка «OK») | `timer` уходит только после нажатия «OK» |
| FR-A-08 | Приложение показывает оставшееся время текущего отсчёта | В UI видно `02:59:41` |
| FR-A-09 | Приложение доставляет уведомления, пока Foreground Service жив | После сворачивания приложения уведомление приходит (AC-04) |
| FR-A-10 | Приложение переподключается к серверу автоматически с backoff 1…60 с | Разрыв сети на 2 мин → восстановление без перезапуска приложения |
| FR-A-11 | Приложение хранит токен в зашифрованном хранилище | Токен отсутствует в `adb shell dumpsys` в открытом виде; читается только приложением |
| FR-A-12 | Приложение позволяет посмотреть `device_id`, `fw` кнопки | Экран «Оборудование» с полями |
| FR-A-13 | Приложение отображает состояние кнопки (`ARMED/ACTIVE/…`) | Состояние приходит в `status` и отображается |
| FR-A-14 | Приложение не отправляет `timer`, если кнопка офлайн | Кнопка `OFFLINE` → кнопка «OK» неактивна, подпись поясняет причину |
| FR-A-15 | Приложение умеет отменять активный отсчёт (кнопка «Отменить») → отправляет `cancel` | Кнопка получает `cancel` и возвращается в `ARMED` |
| FR-A-16 | После нажатия «OK» приложение ждёт подтверждения от кнопки не дольше 10 с; при отсутствии — показывает «Кнопка не отвечает, время не установлено» и предлагает повторить | `timer` отправлен, `ack` не пришёл за 10 с → сообщение об отказе, повтор доступен |
| FR-A-17 | Приложение не заявляет об успешной отправке, пока не получило подтверждение: до получения `ack` статус доставки — «Ожидание подтверждения…» | В UI нет состояния «отправлено», если `ack` не получен |

## 5. Нефункциональные требования

### 5.1 Производительность и задержки

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Задержка «нажатие → уведомление в приложении» | p50 ≤ 800 мс, p95 ≤ 2 с |
| NFR-02 | Задержка «подтверждение ETA → отсчёт на OLED» | p95 ≤ 2 с |
| NFR-03 | Задержка обнаружения смерти клиента (heartbeat). Влияет только на индикатор статуса; критичный путь защищён таймаутом подтверждения FR-A-16 | ≤ 45 с (3 heartbeat-пинга по 15 с) |

## 6. Протокол

Подробная спецификация — в файле `Протокол.md`. Здесь — ключевые решения.

### 6.1 Транспорт и аутентификация

- `ws://<host>:<port>/ws`
- Токен **не** в URL. Первым кадром клиент шлёт `hello` с токеном; сервер отвечает `hello_ok` или закрывает соединение кодом `4401`.
- Роли: `device`, `app`.
- Идентификаторы: `device_id` (8 hex-символов, генерируется при первом запуске и хранится в NVS), `app_id` (такой же формат, генерируется приложением при установке).

### 6.2 Сообщения (JSON, UTF-8)

| Направление | Тип | Назначение |
|---|---|---|
| клиент → сервер | `hello` | аутентификация и регистрация роли |
| сервер → клиент | `hello_ok` | подтверждение, серверное время, сохранённое состояние |
| кнопка → сервер | `press` | сигнал о нажатии |
| сервер → приложение | `press` | доставка сигнала |
| приложение → сервер | `timer` | новое значение ETA |
| сервер → кнопка | `timer` | доставка ETA |
| приложение → сервер | `cancel` | отмена отсчёта |
| сервер → кнопка | `cancel` | доставка отмены |
| клиент → сервер | `ack` | подтверждение приёма |
| сервер → клиент | `ack` | подтверждение приёма |
| сервер → обе | `status` | живость и состояние партнёра |
| обе | `ping` / `pong` | heartbeat |
| сервер → клиент | `error` | ошибка протокола с кодом |

### 6.3 Время

**Источник истины по времени — сервер.** Кнопка не имеет батарейки RTC, поэтому её локальные часы обнуляются при каждом цикле питания.

- Сервер включает в каждый ответ поле `t` — его текущее время UTC в секундах epoch.
- Кнопка при каждом соединении вычисляет смещение `off = server_t − device_now` и сохраняет его в NVS.
- Текущее «серверное» время кнопки = `device_now + off`.
- Дедлайн отсчёта хранится в NVS как абсолютный epoch в серверной шкале.
- При каждом пробуждении `remaining = deadline − (device_now + off)`.
- **Детект потери питания:** если `device_now` после старта меньше сохранённого `last_seen_t`, значит часы сбросились → отсчёт недействителен, кнопка показывает `TIMER LOST` (AC-08) и ждёт новой команды.
- Погрешность смещения: часы ESP32 идут от собственного кварца (ppm-десятки), расхождение с сервером — единицы минут за сутки. На точность отсчёта в пределах сессии это не влияет, потому что смещение фиксируется в момент соединения.

Итог: **NTP кнопке не нужен**, а точность отсчёта не зависит от локальных часов.

### 6.4 Доставка и подтверждения

Двухуровневое подтверждение, как в черновике `helpful materials.md` («гарантия доставки — получатель должен вернуть ответ»):

```
кнопка --press(seq=7)--> сервер --ack(seq=7, ok)--> кнопка
                              |
                              +--press(seq=7)--> приложение --ack(seq=7)--> сервер --ack(seq=7, delivered)--> кнопка
```

- Кнопка показывает `SENT` после `ack(ok)` от сервера и `DELIVERED` после `ack(delivered)` от приложения.
- Если `ack(delivered)` не пришёл за 30 с — `NO ACK` + звук ошибки (FR-K-08).
- `seq` монотонный, сервер отбрасывает дубликаты (защита от повторной доставки при reconnect, NFR-15).

### 7.1 Распиновка

**Pull-up кнопок задавать явно.** Внутренние pull-up/pulldown по умолчанию включены только на strapping-пинах (в том числе GPIO5 — на нём кнопка была в MVP, поэтому работала без `pinMode`). У GPIO4 и GPIO27 pull-up по умолчанию **выключен** → вход плавает. В прошивке: `Pin(4, Pin.IN, Pin.PULL_UP)` и `Pin(27, Pin.IN, Pin.PULL_UP)`.

**GPIO2 (встроенный LED) — strapping-пин.** Для входа в последовательный загрузчик GPIO2 должен быть LOW или плавающим. Светодиод платы подключён к GND через резистор и тянет вывод вниз, поэтому загрузчик остаётся доступен. Но если активный уровень окажется LOW (LED горит при LOW), то удержание GPIO2 в HIGH ради «погашенного» LED в deep sleep и блокирует USB-флаш, и жжёт 5–10 мА. Полярность и ток в каждом состоянии замеряются в R0 (шаг 1).

**BTN2 не будит из deep sleep — и это нормально.** ext1 на ESP32 умеет только `ANY_HIGH` / `ALL_LOW`; две кнопки с pull-up через него не разбудить. ext0 работает с одним пином и внутренним pull-up (RTC-домен остаётся включённым), внешние резисторы не нужны. Отмена таймера и mute нужны, когда кнопка уже проснулась, — все сценарии покрыты. После пробуждения `machine.wake_pins()` покажет, какая кнопка сработала.

Ограничения по питанию: `3V3` — **выход** AMS1117, `VIN` — вход 5 В. Питать кнопку через `3V3` «снаружи» нельзя: при подключённом USB это даёт обратное питание в порт.

### 7.2 Дисплей

**Модуль OLED 0.96" SSD1306, 128×64, I2C, адрес `0x3C`, выводы SDA=GPIO21, SCL=GPIO22.** Все параметры подтверждены рабочим кодом из `legacy/lamalarma` и `legacy/sdd1306_test`, а не предположением.

Доказательства из кода:

| Факт | Откуда |
|---|---|
| I2C, не SPI | `Adafruit_SSD1306 display(128, 64, &Wire, OLED_RESET)` — конструктор с `&Wire` |
| 4 вывода, RESET не используется | `OLED_RESET = -1` |
| Адрес `0x3C` | `display.begin(SSD1306_SWITCHCAPVCC, 0x3C)` — явным адресом, не по умолчанию |
| SDA=21, SCL=22 | `Wire.begin()` без аргументов → дефолтные пины варианта `esp32` (`pins_arduino.h`: `SDA = 21`, `SCL = 22`) |
| Контроллер — SSD1306, не SH1106 | Adafruit_SSD1306 2.5.15 не содержит поддержки SH1106 и шлёт `0x21`/`0x22` (page/column addressing), которых у SH1106 нет — картинка уехала бы влево на 2 px с мусором справа. В `lamalarma` рисуется битмап `moon` ровно 128×64 во всю ширину; при SH1106 он был бы разорван. Оба проекта работали |
| Питание 3.3 В от `VDD` | `SSD1306_SWITCHCAPVCC` — внутренний charge pump, внешний boost не нужен |

Надпись «SCK» на модуле — это **SCL** (дешёвые модули часто так маркируют). Надпись из `helpful materials.md` про «38pin» относится к плате, не к дисплею.

Требования к дисплею:

- Ток до 20 мА при полностью белом экране; `display off` — 0.1–0.5 мА.
- Подтягивающие резисторы I2C (4.7 кОм) — обычно распаяны на модуле; при отсутствии — добавить.
- Текст: собственный шрифт 5×7 (ASCII), масштабирование ×2 для таймера. Кириллица не требуется.
- Разрешение 128×64 достаточно: таймер `HH:MM:SS` в масштабе ×2 занимает 6 символов × 12 px = 72 px — помещается по центру.
- **Битмапы из `legacy/lamalarma/include/` (`moon.h`, `kitler.h`) переносятся в прошивку как splash-экран.** Формат — GFX row-major, ровно 1024 байта на 128×64; framebuf MicroPython совпадает, но SSD1306 ждёт page-major (8 страниц по 128 байт) → нужен конвертер, ~20 строк. Как замена шрифту не годятся: шрифт 5×7 всё равно нужен для `HH:MM:SS` и служебных надписей.

Драйвер дисплея в проекте пишется свой (нужен собственный шрифт, управление `display off` и page-major вывод). Локальные исходники `legacy/lamalarma/.pio/libdeps/.../Adafruit SSD1306/Adafruit_SSD1306.cpp` удалены при чистке артефактов, но библиотека восстанавливается одной командой `pio pkg install` — использовать как референс init-последовательности: `init1`/`init2`/`init3`, режим `0x20 0x00` (горизонтальная адресация), `0x21`/`0x22`, `0x8D 0x14` (charge pump).

### 7.3 Звук

Ответ на вопрос из `helpful materials.md` («какие динамики есть для ESP без дополнительной платы?»):

- **Пассивный пьезо-бузер + NPN-транзистор S8050 + резистор 1 кОм в базе, вывод GPIO23.** Динамик при таком подключении — это пьезоизлучатель, а не «динамик». Управляется ШИМ (`machine.PWM`, `duty_u16`), позволяет менять тон.
- **Почему GPIO23, а не GPIO17.** GPIO16/17 принадлежат домену VDD_SDIO, который в deep sleep гасится — база транзистора останется «плавающей» и бузер может щёлкнуть. GPIO23 — обычный домен VDD3P3, состояние сохраняется. ESP-IDF предупреждает про GPIO16/17 на WROOM-32 прямо.
- Настоящий конический динамик без усилителя не даёт приемлемой громкости. Потребуется усилитель (PAM8403 и подобные) — это отдельная плата, в текущий BOM не входит.
- Выходы DAC ESP32 (GPIO 25/26) позволяют получить аналоговый сигнал напрямую, но громкость мала, а шум высок. Используется только как резерв.
- Активный бузер (со встроенным генератором) не подходит: он умеет только пищать, без управления тоном и длительностью.
- В MVP (`legacy/lamalarma`) звука не было вовсе — схема не реализовывалась и проверяется в R0.

### 7.4 Световая индикация

Два индикатора: **внешний LED OK на GPIO19** (1 кОм, активный низ — светодиод на GND) и **встроенный LED ERR на GPIO2** (светодиод самой платы, экономия BOM).

> Встроенный светодиод расположен на плате, а плата будет внутри 3D-печатного корпуса. В релиз R3 входит требование предусмотреть в корпусе **окно или световод** под встроенный LED — иначе состояние ошибки в поле не видно. Состояния ошибки дублируются на OLED и звуком, поэтому критичной информации потеря не несёт.

Полярность встроенного LED на GPIO2 не проверена: в MVP (`legacy/lamalarma`) он был объявлен как `LED 2`, но `digitalWrite` там закомментирован — фактического мигания не было. Активный уровень и ток в каждом состоянии замеряются в R0 (шаг 1). Если LED окажется активным по LOW, то удержание GPIO2 в HIGH ради «погашенного» LED в deep sleep одновременно блокирует вход в USB-загрузчик (GPIO2 — strapping-пин) и добавляет 5–10 мА; в этом случае индикацию переносят на GPIO23.

| Состояние | LED OK (GPIO 19) | LED ERR (GPIO 2) | Звук |
|---|---|---|---|
| `NO SERVER` | гаснет | горит | тройной низкий |
| `ARMED` | горит | гаснет | короткий тихий |
| `SENT` (ждём ACK) | мигает 2 Гц | гаснет | — |
| `NO ACK` | гаснет | мигает 2 Гц | двойной низкий |
| `WAIT_ETA` | мигает 1 Гц | гаснет | — |
| `COUNTDOWN` | горит | гаснет | одиночный высокий |
| `ARRIVED` | мигает 4 Гц | гаснет | мелодия из трёх нот |
| MUTE | горит (тускло) | — | звук выключен |

### 7.5 Питание

Схема (рекомендуемая):

```
   USB-C (зарядка)  ──►  зарядный модуль с power-path (MCP73871 / BQ24074)
                             │                    │
                             │  системный выход    │  выход в систему
                             ▼                    ▼
                        18650 3000 мА·ч      ┌──────────────────────────┐
                       (в защитном           │  SPDT-тумблер SW1         │
                        держателе)           │  OFF / USB / BAT          │
                                               └───────┬──────────┬───────┘
                                                       │          │
                                            USB-C платы (5 В)   boost 3.0–4.2 → 5.0 В
                                                       │          │
                                                       └────┬─────┘
                                                            ▼
                                                    вывод VIN платы
                                                            │
                                                     AMS1117 → 3.3 В
```

Ключевые требования:

1. **Тумблер — физический размыкатель источника.** Ни DOIT 36-пиновый клон, ни DevKitC не имеют развязки между USB и входом питания: подача 5 В на `VIN` при подключённом USB даёт обратное питание в порт. Тумблер в положении `USB` разрывает питание от boost-конвертера, поэтому одновременное присутствие аккумулятора и кабеля безопасно (NFR-12).
2. **Зарядка с power-path.** Обычный TP4056 неправильно завершает заряд при подключённой нагрузке. Нужен модуль с power-path и load-sharing (MCP73871, BQ24074) либо зарядка только при выключенной кнопке.
3. **Boost-конвертер** — на 5.0 В, ток ≥ 1 А (пик Wi-Fi TX — до 240 мА при 3.3 В, с запасом).
4. **Предохранитель** — PPTC 1.1 А на положительном выводе аккумулятора.
5. **Обход AMS1117** (опционально, для экономии): питать вывод `3V3` напрямую с boost-конвертера на 3.3 В. Экономия ~0.2–0.4 Вт в ACTIVE. Применять только если тумблер гарантирует, что USB в этот момент не подключён.

> **Внимание, названия выводов на этой плате:** вход питания — `VIN` (внизу левого ряда), `3V3` — выход стабилизатора (внизу правого ряда). Вывода `5V` здесь нет. В схеме выше boost подключается к `VIN` платы, а не к «5V».

### 7.6 Корпус

- 3D-печать (PLA/PETG). Требования: посадочное место под вырез в OLED, отверстия под кнопки, светодиоды, тумблер и разъём USB-C; доступ к выводам для программирования (в открытом состоянии) или через отверстия.
- **Окно или световод под встроенный светодиод платы (GPIO2, LED ERR).** Без этого состояние ошибки в поле не видно — плата с LED лежит внутри корпуса (§7.4).
- Отдельный отсек под аккумулятор с термоизоляцией от цепи.
- Звуковое отверстие (диаметр ≥ 6 мм) для пьезо-бузера.
- Объём: ориентир 90×60×30 мм.

## 8. Энергопотребление и расчёт автономности

### 8.1 Токи (ESP32-WROOM-32)

| Режим | Ток |
|---|---|
| Wi-Fi TX (пик) | 240 мА |
| Wi-Fi активный, редкий трафик | 80–120 мА |
| Modem sleep (DTIM3) | 20 мА |
| Deep sleep + RTC-таймер | 10 мкА |
| OLED SSD1306, экран включён | 20 мА |
| OLED SSD1306, `display off` | 0.1–0.5 мА |
| AMS1117, quiescent | ≈ 5 мА |
| CP2102 + светодиод питания платы | ≈ 1–8 мА |

### 8.2 Почему важен выбор режима

Потребление самой ESP32 в deep sleep (10 мкА) на фоне обвязки дешёвой клиновидной платы (5–10 мА) — ничтожно. **Управляет всем расходом обвязка платы и OLED**, а не микроконтроллер.

Отсюда два решения:

1. **В IDLE OLED выключается** (`display off`), а кадр обновляется при каждом пробуждении. Экономия — до 20 мА, то есть срок жизни растёт примерно втроих.
2. **Гасится светодиод питания платы** (перепайка резистора или отключение), если целевой срок IDLE — 7+ суток. Экономия 1–8 мА.

Отдельно про встроенный светодиод на GPIO2: он используется как **индикатор LED ERR** (§7.4), а не как индикатор питания, поэтому в IDLE его нужно гасить программно. Если он окажется активным по LOW (полярность проверяется в R0), то удержание GPIO2 в HIGH ради «погашенного» LED добавит 5–10 мА и заблокирует USB-загрузчик — тогда индикация переносится на GPIO23, а GPIO2 остаётся свободным.

### 8.3 Сценарии и оценка

| Сценарий | Средний ток | 18650 3000 мА·ч (реальная ёмкость ~85 %) |
|---|---|---|
| IDLE, OLED выключен, LED платы перепаян | ≈ 5 мА | ≈ 21 сутки |
| IDLE, OLED выключен, LED платы штатно | ≈ 7 мА | ≈ 15 суток |
| IDLE, OLED включён постоянно | ≈ 27 мА | ≈ 4 суток |
| ACTIVE (Wi-Fi + OLED + таймер) | ≈ 130 мА | ≈ 20 ч |
| ACTIVE с boost-конвертером на 3.3 В (обход AMS1117) | ≈ 120 мА | ≈ 21 ч |

Оценки — расчётные, требуют замера (NFR-09, NFR-10). **Замер входит в релиз R3.**

### 8.4 Программа замера

1. Собрать стенд: плата + OLED + бузер + аккумулятор, питание от лабораторного БП с амперметром.
2. Замерить ток в состояниях: BOOT, WIFI_CONNECT, OFFLINE, ARMED, ACTIVE, IDLE (30 с), ARRIVED.
3. Замерить ток deep sleep отдельно (пробуждение раз в 60 с).
4. Замерить падение заряда за 24 ч в IDLE, экстраполировать автономность.
5. Результаты — в `docs/power measurements.md`.

### 11.1 Стенд R0 — что именно проверяется

Порядок проверок на стенде:

1. **Встроенный LED на GPIO2.** Определить активный уровень (HIGH или LOW зажигает) и снять ток в обоих состояниях. Если LED активен по LOW — перенести индикацию на GPIO23 (R-17). Отдельно проверить, что USB-загрузчик остаётся доступным: GPIO2 — strapping-пин, вход в загрузчик требует LOW или плавающего состояния.
2. **I2C-дисплей.** `I2C(0, sda=Pin(21), scl=Pin(22))` → `scan()` должен вернуть `0x3c`. Вывести текст, таймер `HH:MM:SS` в масштабе ×2, splash-экран из `moon.h` (конвертер page-major, §7.2).
3. **Кнопки.** BTN1 на GPIO4, BTN2 на GPIO27, оба с **явным** `Pin.IN | Pin.PULL_UP` (R-14). Проверить, что состояние покоя — HIGH, нажатие — LOW, и что чтение стабильно без `pinMode`-зависимостей.
4. **Пробуждение по кнопке.** `esp32.wake_on_ext0(Pin(4), esp32.WAKEUP_ALL_LOW)` + `machine.deepsleep()` → кнопка будит устройство. После пробуждения `machine.wake_pins()` показывает GPIO4.
5. **Бузер на GPIO23.** Пассивный пьезо через S8050: тон, громкость, отсутствие щелчка при входе в deep sleep (R-16 — именно для этого бузер уведён с GPIO17).
6. **Deep sleep.** Замерить ток IDLE отдельно; убедиться, что OLED погашен (`display off`), оба светодиода погашены, бузер молчит.
7. **Внешний LED на GPIO19** (1 кОм, активный низ) — свечение во всех состояниях таблицы §7.4.

### 11.2 Definition of Done (общее)

- Требования имеют тест или процедуру проверки.
- Прошивка и сервер запускаются по инструкции из `README.md` на чистой машине.
- Протокол покрыт описанием всех сообщений и кодов ошибок.
- Логи не содержат токенов и персональных данных (проверка grep по журналу).
- **В исходниках нет ни токена WS, ни пароля/имени точки доступа, ни токена Telegram-бота** — проверка grep по репозиторию. Прецедент: в `legacy/lamalarma/src/main.cpp` токен бота и пароль Wi-Fi лежали открытым текстом (R-18).
- Замеры токов приложены к `docs/`.
- Значения `device_id` и `app_id` — в конфиге, в коде прошивки нет.
