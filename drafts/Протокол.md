# Nightcall — Протокол WebSocket

**Версия:** 1.1
**Дата:** 2026-11-02 (1.1 — 2026-11-27: §4.10 `register_push`, FCM-доставка `press`)
**Связан с:** `ТЗ.md` §6

Источник правды для трёх реализаций: прошивки кнопки (MicroPython), сервера (Python) и приложения (Kotlin). При расхождении с кодом — правься здесь.

---

## 1. Транспорт

| Параметр | Значение |
|---|---|
| Схема | `ws://` (без TLS — принятый риск, `ТЗ.md` NFR-21) |
| Эндпоинт | `ws://<host>:<port>/ws` |
| Формат кадров | JSON, UTF-8, без BOM |
| Максимальный размер сообщения | 4096 байт (FR-S-12) |
| Heartbeat | пинг каждые 15 с, 3 пропуска → закрытие сессии |
| Таймаут ожидания ACK | 30 с |

Порт по умолчанию: `8000` (конфигурируется через переменную окружения).

---

## 2. Жизненный цикл сессии

```
клиент                                   сервер
  │─── TCP connect ───────────────────────►│
  │─── HTTP Upgrade /ws ───────────────────►│
  │◄── 101 Switching Protocols ─────────────│
  │                                        │
  │─── {"t":"hello", ...} ─────────────────►│   проверка токена и роли
  │                                        │
  │              (ошибка)  ◄── {"t":"error"} │
  │◄──── close 4401 / 4400 ─────────────────│
  │                                        │
  │◄─── {"t":"hello_ok", ...} ──────────────│
  │                                        │
  │◄───────── {"t":"status", ...} ──────────│   состояние партнёра
  │                                        │
  │◄───────── {"t":"ping"} ─────────────────│   каждые 15 с
  │─── {"t":"pong"} ───────────────────────►│
```

**Правила:**

1. До `hello` сервер не принимает никаких других сообщений. Любое другое сообщение → close `4400`.
2. `hello` — первое сообщение, отправляется сразу после Upgrade. Таймаут на `hello`: 10 с, иначе close `4400`.
3. Токен **никогда** не передаётся в URL и не пишется в лог (FR-S-10).
4. Повторный `hello` в рамках одной сессии → close `4400`.
5. Сервер может закрыть соединение в любой момент. Клиент обязан переподключаться сам (§6).

## 3. Идентификаторы

| Поле | Формат | Кто генерирует | Где хранится |
|---|---|---|---|
| `device_id` | 8 hex-символов, lowercase | Кнопка при первом запуске | NVS кнопки |
| `app_id` | 8 hex-символов, lowercase | Приложение при установке | `EncryptedSharedPreferences` |
| `seq` | целое, монотонное от 1 | Отправитель | Не хранится, защита от дублей |

`device_id` и `app_id` — не секреты. Токен — секрет.

## 4. Сообщения

### 4.1 `hello` — клиент → сервер

```json
{
  "v": 1,
  "t": "hello",
  "role": "device",
  "token": "9f2c…",
  "id": "a1b2c3d4",
  "fw": "1.0.0"
}
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `v` | int | да | Версия протокола. Сервер отклоняет мажорную версию ≠ 1 (NFR-37) |
| `t` | string | да | Тип сообщения |
| `role` | string | да | `device` \| `app` |
| `token` | string | да | Секрет. Сравнивается с SHA-256 от известного токена |
| `id` | string | да | `device_id` или `app_id` |
| `fw` | string | нет | Версия прошивки (только для `device`) |

Ответ при ошибке:

```json
{ "v": 1, "t": "error", "code": "auth_failed", "msg": "bad token" }
```
→ соединение закрывается кодом **4401**.

Некорректная роль или отсутствие `id` → `error` с кодом `bad_request`, close **4400**.

### 4.2 `hello_ok` — сервер → клиент

```json
{
  "v": 1,
  "t": "hello_ok",
  "session": "s-7f3a91",
  "t_epoch": 1793001234,
  "peer": { "id": "a1b2c3d4", "online": true, "state": "ARMED", "remaining_s": 10800 }
}
```

| Поле | Описание |
|---|---|
| `session` | Идентификатор сессии для логов |
| `t_epoch` | **Текущее время сервера, UTC epoch-секунды.** Клиент вычисляет смещение `off = t_epoch − device_now` |
| `peer` | Состояние партнёра, если он подключён. `online: false`, если партнёра нет |

`peer.state` — строка из набора: `BOOT`, `OFFLINE`, `ARMED`, `SENT`, `WAIT_ETA`, `COUNTDOWN`, `ARRIVED`, `NO_ACK`.

### 4.3 `press` — кнопка → сервер → приложение

Кнопка:

```json
{ "v": 1, "t": "press", "seq": 7, "t_epoch": 1793001234 }
```

Сервер пересылает приложению, добавляя отправителя:

```json
{ "v": 1, "t": "press", "seq": 7, "t_epoch": 1793001234, "from": "a1b2c3d4" }
```

### 4.4 `timer` — приложение → сервер → кнопка

Приложение:

```json
{ "v": 1, "t": "timer", "seq": 3, "duration_s": 10800, "t_epoch": 1793001300 }
```

| Поле | Тип | Ограничение |
|---|---|---|
| `duration_s` | int | 60…86400 (1 минута … 24 часа). Вне диапазона → сервер отвечает `error` `bad_duration` и **не пересылает** |
| `t_epoch` | int | Момент отправки (сервер всё равно пересчитает смещение) |

Сервер пересылает кнопке, добавляя дедлайн:

```json
{ "v": 1, "t": "timer", "seq": 3, "duration_s": 10800, "deadline_t": 1793012100, "t_epoch": 1793001300 }
```

`deadline_t` = абсолютный epoch в серверной шкале. Кнопка сохраняет его в NVS и считает `remaining = deadline_t − (device_now + off)`.

### 4.5 `cancel` — приложение → сервер → кнопка

```json
{ "v": 1, "t": "cancel", "seq": 4, "t_epoch": 1793001400 }
```

Кнопка прекращает отсчёт и возвращается в `ARMED`.

### 4.6 `ack` — в обе стороны

```json
{ "v": 1, "t": "ack", "seq": 7, "ok": true, "stage": "server" }
```

| Поле | Описание |
|---|---|
| `seq` | `seq` подтверждаемого сообщения |
| `ok` | `false` — сообщение отвергнуто (с причиной в `error`) |
| `stage` | `server` — сервер принял и передал; `delivered` — конечный получатель принял |

Кнопка различает: `ack(stage=server)` → экран `SENT`; `ack(stage=delivered)` → экран `WAIT_ETA`.

**Ожидание подтверждения приложением.** Приложение, отправив `timer`, обязано дождаться `ack(seq=<timer.seq>, stage=delivered)` в течение **10 с** (FR-A-16). До получения `ack` состояние доставки — «Ожидание подтверждения…»; приложение не имеет права показывать «отправлено». По истечении 10 с приложение показывает «Кнопка не отвечает, время не установлено» и предлагает повторить отправку.

Таймаут 10 с не зависит от heartbeat: сервер может закрыть сессию кнопки по отсутствию пингов (45 с), но приложение узнаёт об отказе гораздо раньше — по собственному таймауту подтверждения. Поэтому задержка обнаружения смерти клиента (NFR-03) затрагивает только индикатор статуса, а не доставку.

Повторная отправка `timer` с тем же `seq` допустима: сервер отбрасывает дубликаты по `seq` (NFR-15), но приложение при повторе использует **новый** `seq`, чтобы сервер счёл это новой командой.

### 4.7 `status` — сервер → обоим

```json
{
  "v": 1,
  "t": "status",
  "t_epoch": 1793001500,
  "device": { "online": true, "state": "COUNTDOWN", "remaining_s": 10412, "fw": "1.0.0" },
  "app":    { "online": true }
}
```

Отправляется при: изменении живости любого клиента, смене состояния кнопки, старте сессии.

### 4.8 `ping` / `pong`

```json
{ "v": 1, "t": "ping", "t_epoch": 1793001600 }
{ "v": 1, "t": "pong", "t_epoch": 1793001600 }
```

Сервер шлёт `ping` каждые 15 с; клиент обязан ответить `pong` в течение 10 с. Три пропуска подряд → сервер закрывает сессию и удаляет клиента из реестра (NFR-03).

Клиент (кнопка) дополнительно шлёт `ping` раз в 20 с — чтобы обнаружить «мёртвый, но ещё не закрытый» сокет.

### 4.9 `error` — сервер → клиент

```json
{ "v": 1, "t": "error", "code": "bad_duration", "msg": "duration_s out of range", "seq": 3 }
```

| Код | Смысл | Действие клиента |
|---|---|---|
| `auth_failed` | Неверный токен | Закрыть соединение, не переподключаться, показать `AUTH FAIL` |
| `bad_request` | Нарушен протокол | Закрыть соединение, переподключиться с backoff |
| `bad_duration` | `duration_s` вне диапазона | Показать ошибку ввода в приложении |
| `no_peer` | Нет подключённого партнёра | Кнопка: `NO APP`; приложение: `NO BUTTON` |
| `duplicate` | Дубликат `seq`, уже обработан | Игнорировать |
| `internal` | Внутренняя ошибка сервера | Переподключиться с backoff |

### 4.10 `register_push` — приложение → сервер (v1.1)

Приложение сообщает FCM-токен, чтобы сервер мог доставить вызов, когда WebSocket-сессия не установлена (приложение выгружено системой или процесс убит).

```json
{ "v": 1, "t": "register_push", "token": "cZ1x...:APA91b...", "t_epoch": 1793001700 }
```

| Поле | Тип | Ограничение |
|---|---|---|
| `token` | string | 1…4096 символов, без пробелов |
| `t_epoch` | int | Момент отправки (для логов) |

- Сообщение идемпотентно и не имеет `seq`: приложение отправляет его после каждого `hello_ok` и при смене токена (`onNewToken`); `ack` не требуется.
- Сервер хранит токен для `app_id` на диске (переживает перезапуск) и **никогда не пишет его в лог**; на ответ FCM `UNREGISTERED` — удаляет.
- Отправитель — только приложение; от кнопки → `error` `bad_request`.

**Доставка `press`.** Если токен зарегистрирован, сервер на каждый `press` дополнительно отправляет FCM data-сообщение с полями `v`, `t`, `seq`, `t_epoch`, `device_id` (вместо `from`: этот ключ зарезервирован FCM) и `priority=high`. WebSocket остаётся основным каналом, поэтому доставка «как минимум один раз»: приложение обязано дедуплицировать по `(from, seq, t_epoch)`, иначе одно нажатие даст два уведомления. `ack(stage=delivered)` по-прежнему идёт только по WebSocket: «доставлено» = «приложение приняло».

## 5. Коды закрытия WebSocket

| Код | Когда |
|---|---|
| 1000 | Штатное закрытие |
| 4400 | Нарушение протокола (неверная роль, нет `hello`, превышен размер) |
| 4401 | Ошибка аутентификации |
| 1011 | Внутренняя ошибка сервера |

## 6. Переподключение клиента

Экспоненциальный backoff с джиттером:

```
delay = min(60, 2^attempt) ± 20 %     attempt = 0, 1, 2, ...
```

| Попытка | Задержка |
|---|---|
| 1 | 1 с |
| 2 | 2 с |
| 3 | 4 с |
| 4 | 8 с |
| 5 | 16 с |
| 6+ | 30–60 с (с джиттером) |

- Сбросить счётчик попыток при успешном `hello_ok`.
- **Кнопка в режиме ACTIVE:** максимальная задержка 10 с (таймер идёт, нужна быстрая реакция).
- **Кнопка в режиме IDLE:** максимальная задержка 60 с (пробуждение по таймеру, §8 `ТЗ.md`).
- **Приложение:** максимальная задержка 60 с.

При переподключении клиент обязан заново отправить `hello` (сессия новая).

## 7. Требования к реализации клиента WS на MicroPython

Критично: **в `micropython-lib` нет WS-клиента**. `extmod/modwebsocket.c` — это WebREPL-сервер для ESP8266, не клиент. Клиент пишется вручную.

### 7.1 Handshake

```
GET /ws HTTP/1.1
Host: <host>:<port>
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <base64 16 случайных байт>
Sec-WebSocket-Version: 13

```

Ожидается `HTTP/1.1 101` и заголовок `Sec-WebSocket-Accept`, равный
`base64(sha1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`.

Проверить код ответа и наличие `Upgrade: websocket` **до** чтения первого WS-кадра: иначе байты HTTP-ответа попадут в разбор кадра.

### 7.2 Кадры

- Бит 0: `FIN`. Биты 1–3: opcode. Бит 4: `MASK`. Биты 5–7: длинаpayload (7 / 7+16 / 7+64).
- **Клиент обязан маскировать** кадры (бит MASK = 1), ключ — 4 случайных байта, payload XOR ключ.
- Сервер кадры не маскирует.
- Opcode: `0x1` text, `0x2` binary, `0x8` close, `0x9` ping, `0xA` pong, `0x0` continuation.
- Фрагментация: сервер вправе прислать продолжение (`0x0`) — нужно собирать до `FIN=1`. Собственный клиент **не фрагментирует** исходящие сообщения: payload ≤ 4 КБ всегда помещается в один кадр.
- Обработка `ping` от сервера: ответить `pong` с той же payload.
- `close`: получить → ответить `close` и закрыть сокет.

### 7.3 Таймауты и ввод-вывод

- `socket.settimeout()` + `select.poll()` для мультиплексинга; в MicroPython на ESP32 доступен `select.poll()`.
- Неблокирующее чтение с собственным дедлайном; отдельный поток/тамер для ping.
- `machine.freq(160_000_000)` — снижает потребление, часы не критичны.

### 7.4 Память

- Буферы переиспользовать: не создавать новый `bytearray` на каждый кадр.
- `gc.mem_free()` в лог при старте и раз в минуту — контроль NFR-45.
- JSON: `import json` (в MicroPython ≥ 1.19 `json` — встроенный быстрый модуль; `ujson` — устаревший алиас).

## 8. Требования к реализации сервера

- `async` обработка, один task на соединение.
- Реестр: `devices: dict[str, DeviceSession]`, `apps: dict[str, AppSession]`.
- Состояние для переподключения: `last_press`, `last_timer`, `last_status` — в памяти + сброс на диск (JSON-файл, FR-S-13).
- FCM (§4.10): токен приложения хранится на диске; при зарегистрированном токене `press` дублируется data-сообщением, ошибка отправки не влияет на `press` и `ack`.
- Токены: в конфиге хранится SHA-256 от токена; сравнение — `hmac.compare_digest`.
- Логи: JSON-строки в stdout, ключи `event`, `device_id`, `app_id`, `session`, `seq`. **Токен не логируется никогда.**
- `GET /api/status` → `{"device": {...}, "app": {...}}` для диагностики.

## 9. Требования к реализации приложения

- OkHttp `WebSocket` — готовый клиент с TLS-расширениями, поддержкой ping/pong и колбэками.
- Foreground Service: `WebSocket` живёт в сервисе, UI подписывается на `StateFlow` из сервиса.
- Токен — в `EncryptedSharedPreferences`, в `WebSocket` передаётся первым кадром `hello`.
- Уведомление о нажатии: канал `signals` (HIGH), уведомление о статусе: канал `status` (LOW).
- FCM (v1.1 §4.10): токен регистрируется через `register_push`; data-сообщение даёт то же уведомление, что и `press` по WebSocket, поэтому дубликаты отсекаются по `(from, seq, t_epoch)`.

## 10. Контрольный пример диалога

```
кнопка                                  сервер                                     приложение
  │ hello(device) ─────────────────────►│
  │◄──── hello_ok(t_epoch, peer=offline) │
  │◄──── status(device.online=true) ────│
  │                                      │
  │ [пользователь жмёт BTN1]            │
  │ press(seq=7) ──────────────────────►│
  │◄──── ack(seq=7, stage=server) ──────│
  │ [экран: SENT]                        │
  │                                      │ press(seq=7, from=…) ──────────────────►│
  │                                      │◄──── ack(seq=7, stage=delivered) ──────│
  │◄──── ack(seq=7, stage=delivered) ───│
  │ [экран: WAIT ETA]                   │                                          │
  │                                      │◄──── timer(seq=3, duration_s=10800) ────┤
  │◄──── timer(seq=3, deadline_t=…) ────│
  │ [экран: 03:00:00]                   │                                          │
  │◄──── ping ──────────────────────────│
  │───── pong ─────────────────────────►│
  │                                      │◄──── status(device.state=COUNTDOWN) ────┤
  │                                      │            [UI: 02:59:41]             │
```
